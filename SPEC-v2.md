# ТЗ v2 — Персональный планировщик времени и задач

**Тип:** личный инструмент (один пользователь, без аккаунтов в v1).
**Платформа:** PWA (работает офлайн, устанавливается на телефон и десктоп).
**Подход к планированию:** детерминированный математический алгоритм — без ИИ/LLM в ядре.
**Google Calendar:** вне v1 (фиксированные события вводятся вручную).

Документ — ревизия исходного ТЗ. Ниже только то, что изменилось или добавилось: две оси классификации, разбор задачи из текста, экран подтверждения, главный экран на 3 дня и балансирующий алгоритм. Разделы исходного ТЗ, не упомянутые здесь, остаются в силе.

---

## A. Модель классификации: три независимые оси

Задача описывается **тремя ортогональными осями**, а не одним списком категорий. Их нельзя смешивать в один enum — на пересечениях это врёт.

| Ось | Значения | Кто задаёт | Роль |
|---|---|---|---|
| **Тип** (`type`) | `fixed` (привязана ко времени) / `flexible` (алгоритм ставит сам) | парсер или пользователь | определяет, планирует ли алгоритм задачу |
| **Характер** (`nature`) | `strategic` (улучшает жизнь вдолгую) / `tactical` (операционка, каждодневное) | парсер или пользователь | определяет цвет на экране и балансирующий множитель |
| **Категория жизни** (`category`) | `work` / `own_business` / `personal_brand` / `personal` / … (настраивается) | пользователь | фильтр на экране «Категории» |

Ключевое: **привязка ко времени (`type`) и характер (`nature`) независимы.** Стратегическая встреча в 15:00 — это `fixed` + `strategic`. Ежедневная рутина без времени — `flexible` + `tactical`.

## B. Разбор задачи из текста (детерминированный keyword-парсер)

### B.1 Что делает
Пользователь пишет задачу свободным текстом (можно надиктовать телефоном и вставить). Парсер на **правилах и словарях** (никакой модели) извлекает поля.

Пример: `«поставь тренировку в 7 утра на каждое второе утро, продолжительность 30 минут»`

| Поле | Источник | Результат |
|---|---|---|
| `title` | остаток строки | «тренировка» |
| `start_time` | regex времени + маркер «утра» | 07:00 → `type = fixed` |
| `recurrence` | словарь интервалов («каждое второе») | каждые 2 дня |
| `duration` | «продолжительность 30 минут» | 30 мин |
| `nature` | триггер «тренировка» → здоровье | `strategic` (низкая уверенность) |
| `importance` | не извлечено | — |

### B.2 Механика
- Словари: время суток, единицы длительности, слова-триггеры повторения («каждый / через / по будням / каждое второе»), таблица «слово → категория/характер».
- Regex: числа, время, длительности, даты.
- Каждому извлечённому полю присваивается **уровень уверенности** (высокий / низкий). Низкая уверенность = поле подсвечивается как требующее проверки.

### B.3 Честная граница подхода
Keyword-парсер надёжен на структурированных фразах и разваливается на свободной речи. «Каждое второе утро» неоднозначно (через день? по чётным датам?). `importance` по словам угадать почти нельзя. Поэтому **разбор текста — это best-effort предзаполнение, а не источник истины.** (Слой LLM-подсказок поверх ядра — по-прежнему P2, ядро остаётся чистой математикой.)

### B.4 Экран подтверждения (главный, а не запасной)
1. Парсер заполняет что смог.
2. **Всегда** показывается экран со всеми полями.
3. Пустые и неуверенные поля **горят красным** — сразу видно, что дописать.
4. Уточняющий вопрос всплывает **только если незаполненное поле блокирует постановку** (у `flexible` нет длительности — без неё не выделить слот; у `fixed` нет времени начала).

Цена ошибки парсера всегда «поправь красное поле», а не «задача встала молча не туда».

## C. Главный экран — 3 дня

Показывает **сегодня + 2 следующих дня**, вертикальный таймлайн по каждому.

- **Цвет блока = ось `nature`:** стратегические и тактические задачи разными цветами.
- **Форма блока = ось `type`:** `fixed` — сплошная заливка на своей минуте; `flexible` — блок с пунктирной рамкой (размещён алгоритмом, можно перетащить).
- **Полоска-итог сверху каждого дня:** доля дня, ушедшая на стратегию vs тактику — дисбаланс виден мгновенно.
- Плавающая кнопка «+» → поле ввода текста (раздел B).

Так один взгляд отвечает на два вопроса: «сколько у меня стратегии vs операционки» (цвет) и «что жёстко стоит vs что расставил алгоритм» (форма).

## D. Алгоритм планирования v2 (детерминированный, объяснимый)

Дополняет §6 исходного ТЗ. Три изменения ядра: **ургентность по «слаку», балансирующий множитель, явная политика перепланирования.**

### D.1 Свободные слоты (как в §6, с уточнением границы «сейчас»)
```
free_slots(day) = working_hours(day) − fixed_events(day) − уже_размещённые_гибкие_чанки(day)
```
Для сегодняшнего дня слоты начинаются с `max(начало_рабочих_часов, сейчас)`. Горизонт планирования = максимум из «2 недели» и самого дальнего дедлайна в пуле.

### D.2 Скоринг задачи (изменён)
```
# Ургентность — по остатку свободного времени до дедлайна («слак»), а не по календарной дистанции
slack        = свободное_время_до_дедлайна − оставшаяся_длительность
urgency = 1                                     если дедлайна нет
urgency = 1 + 1 / max(slack_в_днях, 0.5)        если дедлайн есть   (slack≤0 → максимум срочности)

# Балансирующий множитель — защищает стратегию (цель 33% недельного свободного времени)
TARGET_STRATEGIC = 0.33
strategic_share  = запланировано_стратегического / всё_запланированное_время (за неделю)
balance_factor = 1                                          для tactical
balance_factor = 1 + k · max(0, TARGET_STRATEGIC − strategic_share)   для strategic

priority_score = importance × urgency × balance_factor
```
- **Слак вместо календарных дней** чинит главный дефект v1: давление дедлайна нарастает по мере того, как времени объективно перестаёт хватать, а не только в последний день.
- **balance_factor** самогасящийся: пока стратегия недобирает до 33% — стратегические задачи поднимаются тем выше, чем сильнее провал; дотянулись до цели — множитель = 1 и стратегия перестаёт душить срочную операционку. Прямо решает проблему §1 «срочное вытесняет важное».

### D.3 Сортировка
По `priority_score` убыв. Тай-брейки: ранний дедлайн → меньший `duration_min` → `created_at` → `id` (последние два гарантируют полный детерминизм).

### D.4 Размещение (жадное, с учётом дедлайна)
1. Ищем самый ранний одиночный слот, вмещающий задачу (сколько минут бронировать — см. D.6). Нашли — ставим целиком.
2. Не нашли и `splittable = true`: идём по слотам хронологически, вырезая чанки ≥ `min_chunk_minutes`, пока не наберём длительность или не упрёмся в дедлайн. Остаток меньше `min_chunk` доливается в предыдущий чанк, а не создаёт куцый кусок.
3. `splittable = false`, одиночного слота нет до дедлайна → `at_risk`.
4. Суммарного свободного времени до дедлайна < `duration_min` → `at_risk` с показом дефицита.

### D.5 Политика перепланирования (была не определена в v1)
- Перепланирование **инкрементальное и стабильное:** уже размещённые авто-чанки по умолчанию **не двигаются**, чтобы «Сегодня» не перетасовывался под пользователем.
- Новая задача с более высоким `priority_score` может **вытеснить** ещё не наступивший авто-чанк более низкого приоритета, только если иначе новая задача уходит в `at_risk`. Вытеснение показывается пользователю («сдвинул X, чтобы успеть Y»).
- Ручные (перетащенные/залоченные, R8) чанки не двигаются никогда.
- Триггеры пересчёта: новое `fixed` событие, новая `flexible` задача, ручной сдвиг/лок, **редактирование** задачи, и проход времени чанка без отметки «сделано» (рефлоу остатка).

### D.6 Сколько времени бронировать (было не определено)
У задачи диапазон `duration_min…duration_max`. Правило: бронируем `duration_max`, если свободного времени до дедлайна с запасом; при нехватке сжимаем к `duration_min`. Одно число от пользователя → `min = max`.

### D.7 Целостность задач и буфер (правила против дробления и наложений)
- **Буфер:** вокруг каждого дела резервируется обязательный разрыв `bufferMinutes` (по умолчанию 15 мин) — запас на задержки. Реализован «раздутием» занятых интервалов при расчёте свободных слотов; на краях рабочего дня буфер не нужен.
- **Целостность:** при размещении сначала пытаемся поставить задачу **одним куском** в самый ранний подходящий слот. Дробим только вынужденно.
- **Короткие не дробим:** задачи длительностью ≤ `noSplitUnderMinutes` (90 мин) не дробятся вообще — если целиком не влезает до дедлайна, задача уходит в `at_risk`, а не крошится.
- **Осколок:** при вынужденном дроблении каждый кусок ≥ `minChunkFloorMinutes` (45 мин). Планировщик не оставляет неразмещаемый мелкий хвост (напр. 120+15 превращается в 90+45).
- **Растянули/сжали руками = изменили дело.** Потянув край блока (или поправив время в шторке), пользователь задаёт, **сколько дело длится**, а не «сколько от него влезло сюда»: диапазон `duration_min…duration_max` сдвигается на ту же дельту. Иначе разница повисала бы неразмещённым хвостом — и **укороченное** дело тут же помечалось «не помещается», хотя до укорачивания всё было в порядке (особенно заметно, когда дедлайн уже прошёл: хвосту буквально некуда встать). Перенос без изменения длины длительность дела не трогает.

### D.8 Разбор времени и дня недели (парсер, раздел B)
- Диапазон времени «с 10 до 17» → начало события + длительность (end − start).
- День недели события («Пт», «в пятницу») → ближайшая соответствующая дата (отдельно от дедлайна «до пятницы»).
- Дефолтная длительность по типу дела («встреча» → 90 мин), если не указана явно.
- **Повторы:** «каждый рабочий день» / «по рабочим дням» → пн–пт; «каждый вторник» / «по пятницам» → конкретный день недели; «каждое второе утро», «через день», «ежедневно», «по будням/выходным» — как раньше.
- **Многодневные периоды:** «с 4 по 6 авг», «с 04.08 по 06.08», «4–6 августа» → событие на весь день, повторяющееся внутри периода (`recurrence.until` ограничивает конец). Используется для отпуска, поездок и т.п.

### D.19 Прошедшие дела: «сделано» и «перенести»
На делах, время которых уже прошло, появляются две кнопки:
- **✓ сделано** — дело помечается выполненным и остаётся в календаре приглушённым серым (зачёркнутым), а не исчезает;
- **↷ перенести** — молча дело переносится **только если его дедлайн ещё не истёк** и до дедлайна нашлось свободное место: тогда решение однозначно. Во всех остальных случаях (дедлайн прошёл, дедлайна нет, места до него нет) дело **остаётся на месте**, а на календаре показываются **3 варианта** — выбор за пользователем.

Среди вариантов могут быть места, занятые другим делом, — но только если это дело **можно сдвинуть, не нарушив его собственный дедлайн** (проверяется на копии плана). Такой вариант помечен **↦** и в подсказке указано, кого он подвинет; выбор варианта двигает оба дела разом.

### D.27 Выполнение по частям
Задачу, которую алгоритм разбил на два и более фрагмента, **закрывают по частям**: галочка относится ровно к той части, по которой её нажали, остальные остаются невыполненными. Так виден прогресс по ходу дня, а не «всё или ничего».

- Каждая часть подписана **«2/3»** на блоке в календаре и на карточке экрана одного дня; в шторке — строка **«часть 2 из 3 · ✅ закроет только её · сделано 1 из 3»**.
- Сделанная часть приглушается и зачёркивается, как выполненное дело; счётчик дня («2 из 5») и «осталось» считают части по отдельности.
- Когда закрыты **все** части, закрывается и сама задача (`status = done`).
- Отметка ставится на кусок (`chunk.status = done`) и дальше **неприкосновенна**: прожитое время нельзя переставить, срастить с соседней частью, уступить чужому делу или потерять при «пересчитать план» — в отличие от неотмеченной части, которая после своего времени спокойно перепланируется на будущее (D.5). Место под неё считается занятым, а её минуты — уже размещёнными.
- У цельного дела (один кусок) галочка работает как раньше — закрывает дело целиком; у повторяющегося события приоритет за днём цикла (D.26).

### D.18 Создание задачи в один шаг
Ввод текста → кнопка **«Создать»** (или Ctrl+Enter) → задача сразу разобрана, сохранена и поставлена планировщиком. Отдельного подтверждения нет. Куда её поставил алгоритм, видно по **подсветке блока на 10 секунд**; если дело попало на дату вне текущего вида, календарь **сам прокручивается к ней** (горизонт календаря тянется до самого дальнего дела, так что дела на далёкие даты не теряются); если место не подошло — правится прямо в календаре (шторка деталей, перетаскивание) или откатывается кнопкой «↶ Отменить». Если задача наложилась или не поместилась, сразу показываются варианты (⚠, синие окна, ↦) — см. D.16.

### D.10 Экран размещения (компактный недельный календарь)
После разбора задачи вместо формы показывается **вся неделя (7 колонок)** с предлагаемым местом задачи в ближайшем свободном слоте. Экран без текстовых полей — вся информация читается из самого блока:
- **цвет** = характер (стратегическая / тактическая);
- **толстая сплошная рамка** = привязано ко времени, **пунктир + полупрозрачность** = гибкая;
- **название** написано на блоке, **длительность** видна из его размера и положения;
- **категория** — всплывающий тег сбоку от блока (у правых колонок — слева).

Редактирование как в Google Calendar: **ручки сверху/снизу** — время начала/конца, **тело** — перенос (в т.ч. на другой день), шаг 5 мин. Во время перетаскивания блок полупрозрачный; над занятым (событие ко времени / закреплённый кусок) — краснеет. При отпускании на занятое место дело **остаётся там, куда его отпустили** — молча никуда не переносится: включается обычный разбор наложения (⚠ на блоке, 3 свободных окна, пометка ↦ у мешающих дел), и решение остаётся за пользователем. Над свободным/гибким местом цвет не меняется, гибкие соседи переливаются сами. Ручное размещение **закрепляет** задачу (locked-кусок), гибкие соседи переливаются вокруг неё при сохранении.

### D.12а Накладка видна сразу на экране размещения
Если разобранное время накладывается на существующее дело, предупреждение появляется **сразу при создании задачи**, а не после сохранения: блок черновика краснеет, под календарём — «Накладывается на «…»», в календаре подсвечиваются **3 ближайших свободных окна** (клик по окну или по кнопке переставляет черновик), и есть кнопка **«Перенести текущие события»** — режим, где клик по существующему делу сдвигает его на день вперёд, освобождая место.

### D.12 Задача не помещается — предложение вместо исчезновения
Задача, которую не удалось разместить до дедлайна, **не пропадает молча**. Показывается предупреждение «Не помещается» с причиной (сколько нужно и сколько свободно), и одновременно:
- в календаре подсвечиваются **3 ближайших свободных окна**, куда задача влезает целиком; клик по окну (в календаре или по кнопке в предупреждении) ставит задачу туда и закрепляет её;
- кнопка **«Перенести текущие события»** включает режим выбора: предупреждение скрывается, подвижные дела подсвечиваются, и клик по любому из них заставляет его уступить место — событие «ко времени» сдвигается на день вперёд, у гибкой задачи дедлайн продлевается на день и снимается закрепление. После этого планировщик пересчитывает план, и исходная задача обычно размещается сама.

### D.16 Разрешение проблем прямо в календаре
Отдельных панелей с предупреждениями нет — всё решается на самом календаре, без лишнего шага:
- на проблемном блоке — значок **⚠** (в подсказке видно, с чем накладка);
- **синие окна** в календаре — свободные места, куда можно перенести. Клик по окну — это уже решение: задача сразу встаёт туда и сохраняется, отдельное «Сохранить» не требуется;
- дела, которые могут уступить место, помечены **↦**. Клик по такому делу **не двигает его сам** — вместо этого показываются **3 варианта места уже для него**, и переносится оно только после выбора окна. Если новое дело накладывается сразу на несколько, помечаются **все**;
- дела, которые уже переносили, помечены **↻** (в подсказке — сколько раз), чтобы не гонять одно и то же по кругу;
**Ручное разрешение.** Наложение можно устранить и самому — сдвинуть или укоротить любое из дел прямо в календаре (первый клик по делу с ↦ выбирает его, второй активирует ручки). Как только дела перестали пересекаться, режим выбора и все подсказки с вариантами **исчезают сами**, и обычное перепланирование возобновляется.

**План не перестраивается до решения.** Если новое событие «ко времени» накрывает уже размещённые дела, планировщик **не запускается**: оба дела остаются ровно на своих местах и показываются внахлёст (в половинных дорожках, оба названия читаемы). Пользователь сам решает, кого двигать — новое событие или то, на которое оно наложилось; только после выбора план пересчитывается.

**Ничего не пропадает.** Задача, которую не удалось разместить, показывается в календаре штриховкой с пометкой «не размещено» — на первом из предложенных ей мест. По ней можно кликнуть и выбрать переносить **её** вместо нового события. Среди предлагаемых окон никогда нет текущего места дела.

**Кто двигается первым.** Если только что созданное событие вытеснило чужую задачу, двигать предлагается **само новое событие** (виновник), а не пострадавшая задача — её место уже было согласовано с её дедлайном. В подсказке прямо сказано, кто кого вытеснил.

**Откат.** Внизу экрана есть кнопки **«↶ Отменить»** и **«Вперёд ↷»** (повтор отменённого; новое действие обрывает ветку повтора) (неактивна, пока откатывать нечего). Снимок плана делается перед каждым изменением — созданием задачи, перетаскиванием, изменением полей в шторке, переносом, удалением, отметкой «сделано». Хранится до 20 шагов, кнопку можно нажимать несколько раз подряд. Откат возвращает ровно прежний план, без перепланирования.

**Без цепной реакции.** В качестве «уступающих» предлагаются только те дела, чей сдвиг проверен на копии плана: он должен решать проблему и не порождать новых переносов. Если сдвиг упрётся в другое дело, такой вариант не предлагается вовсе.

### D.14 Одно дело в один момент времени
Календарь исходит из того, что **два дела не могут занимать одно время**. Разведение блоков по ширине — не обычный режим, а временная мера: дорожки появляются только там, где пересечение реально возникло (конфликт двух дел «ко времени» или черновик поверх существующего), чтобы можно было прочитать оба названия. Как только конфликт разрешён, блоки снова занимают всю ширину колонки.

### D.15 Перестроение при изменении условий
Изменение дедлайна в шторке **открепляет** задачу и запускает полный пересчёт: план перестраивается под новые дедлайны всех задач (например, если поменять дедлайны двух задач местами, они меняются местами и в календаре). Вручную закреплённую задачу можно вернуть под управление алгоритма кнопкой **«Открепить»** в шторке.

### D.21 Окно планирования: «не раньше» + «не позже»
Задачу без привязки ко времени можно ограничить **с обеих сторон**: «с 10 по 12 авг нужно сделать отчёт» — алгоритм сам выберет место, но **не раньше 10-го и не позже 12-го**. В модели это пара `earliest` + `deadline`; свободные слоты обрезаются по обеим границам, и время до `earliest` не учитывается при расчёте слака (иначе задача казалась бы менее срочной, чем есть).

Отличие от занятого периода: тот же диапазон дат без слов-маркеров дела («с 4 по 6 авг отпуск») по-прежнему создаёт **событие на дни целиком**. Признак задачи — слова намерения: *нужно, надо, необходимо, успеть, сделать, подготовить, написать, доделать, закончить, сдать* и подобные. В шторке деталей у такой задачи два поля дат: «не раньше» и дедлайн; изменение любого открепляет задачу и перестраивает план.

### D.22 Перенос пальцем
Ручки изменения начала и конца — **24 px** по высоте (у низких блоков автоматически 16 px, чтобы не закрыть середину, за которую блок таскают целиком). Активированный блок и его ручки объявляют `touch-action: none`, поэтому браузер не забирает жест под прокрутку календаря, а `setPointerCapture` удерживает события, даже если палец ушёл за границы блока. Порог начала перетаскивания — 5 px; `pointercancel` завершает жест так же, как обычное отпускание.

### D.26 Настройки повторения
В строке времени у событий «ко времени» есть кнопка **«повторение»** (между временем и ✨). Она открывает отдельную синюю панель под шторкой, поверх календаря, со структурой как в Google Календаре, по-русски:

- **Повторять каждые** `[N]` `[день / неделю / месяц / год]` — единица склоняется под число («каждые 2 недели»); первый пункт списка — **«не повторять»**, он снимает повтор;
- **Повторять в** — кружки `пн вт ср чт пт сб вс` (только для недельного правила, минимум один день);
- для месячного — выбор **«Ежемесячно N-го числа»** или **«Ежемесячно в первый четверг»** (порядковый и день недели считаются от даты события);
- **Заканчивается**: «Никогда» / «Дата» `[поле даты]` / «После `[N]` повторений»;
- **Отмена** и **Готово**.

Правило хранится как `recurrence = { freq, interval, weekdays?, monthMode?, until?, count? }`. Старые формы (`{everyDays}`, `{weekdays}`), которые пишет парсер, продолжают работать — ядро приводит их к общему виду. Разворачивание учитывает: `count` считается от базового вхождения (а не от окна просмотра), 31-е число в коротком месяце и 29 февраля пропускаются, «первый четверг» всегда попадает на нужный день недели.

Повторение доступно только у дел с привязкой ко времени: у гибких задач место выбирает алгоритм, разворачивать нечего.

### D.25 Липкие шапки дней
Дата и день недели каждой колонки **прилипают к верху календаря** (сразу под кнопками), вместе с цветной полоской занятости. На любой глубине вертикальной прокрутки видно, какой это день — листать вверх до 00:00 не нужно. Шапка шкалы времени непрозрачна, поэтому метки часов проезжают под ней, а не поверх дат.

### D.17 Шкала времени
Справа от календаря — шкала часов, а горизонтальные линии сетки идут ровно по часам, так что время каждого события читается с одного взгляда. Все колонки используют **общий диапазон времени** (рабочие часы, расширенные под события вне них), поэтому метки шкалы совпадают с линиями во всех днях.

### D.13 Диапазон главного экрана
Главный экран показывает **3 или 5 дней** (переключатель в правом верхнем углу, выбор сохраняется — `daysVisible`). Календарь **прокручивается по одному дню** в обе стороны (неделя назад, три недели вперёд) с прилипанием к границе дня — день никогда не обрезается пополам. Если первый видимый день не сегодняшний, появляется кнопка **«← Сегодня»**, возвращающая к исходному положению.

### D.11 Активация блока (защита от случайного переноса)
Инструменты переноса **не появляются сами по себе**. Блок сначала нужно активировать:
- **мышь** — обычный клик по событию;
- **сенсор** — долгое нажатие (~400 мс).

При активации рядом с событием (справа, а если не помещается — слева) всплывает **компактная шторка деталей**: время и длительность, название, характер, тип, категория, дедлайн, кнопки «Удалить» / «Готово». Одновременно у блока появляются **ручки сверху/снизу**, и только теперь он поддаётся перетаскиванию. Клик вне блока и шторки снимает активацию — ручки исчезают.

**Что считается занятым при переносе.** Красным помечается только по-настоящему непреодолимое:
- дело с **жёсткой привязкой ко времени** (fixed) — всегда;
- **закреплённая** гибкая задача — только если её саму некуда переставить до её дедлайна.

Во всех остальных случаях (авто-размещённые задачи, закреплённые, но переставимые) перенос **разрешён**: при отпускании подвинутые задачи освобождаются, и планировщик расставляет их заново вокруг нового места.

**Смена типа** (ко времени ↔ гибкая) переносит время и длительность между представлениями (`start`/`durationMinutes` ↔ закреплённый чанк), поэтому задача остаётся на своём месте, а не теряет размещение.

Это работает одинаково для черновика на экране размещения и для **уже сохранённых задач на главном экране**: перенос сохранённой задачи закрепляет её (`locked`), повторяющиеся события поштучно не переносятся (только детали).

### D.24 Шторка события: состав и правила закрытия
Шторка открывается тапом по делу и **закрывается только кнопками**: ✓ (сохранить) или ✕ (вернуть дело в состояние на момент открытия). Тап по календарю, по фону или по другому месту экрана её больше не закрывает — случайное касание не отменяет правки.

Состав (лишнее для конкретного дела не показывается):
- название; дата (значок 📅), начало и конец, длительность, ✨ — перенос фразой;
- характер: **📈 стратегическая** / **⏩ тактическая**;
- тип: 🔒 ко времени / ↻ гибкая;
- **дробление** (только для гибких): **✂ можно дробить** (фрагменты не мельче `minChunkFloorMinutes` = 45 мин) / **🧱 делать целиком**. Переключение открепляет задачу и перестраивает план;
- категория;
- **границы окна** (только для гибких): два значка календаря — «📅 от» (предлайн, не раньше) и «📅 до» (дедлайн). Незаданная граница показана бледной;
- **✅ «сделано» и ↷ «перенести»** — появляются, когда дело **уже идёт или прошло** (раньше эти кнопки жили на самом блоке в календаре);
- 🗑 удалить, ↻ открепить (если закреплено).

При перестроении плана чанки пересоздаются, поэтому активная шторка переключается на актуальный фрагмент той же задачи и не закрывается сама.

**Вид.** Фон шторки — синий, как весь интерфейс; элементы лежат светлыми плитками впритык друг к другу, между ними зазор 3 px, сквозь который и по скруглениям просвечивает фон. Переключатели (характер, тип, дробление) — **слайдеры**: цельная дорожка, внутри которой подсветка перетекает из-под одного значка под другой за 260 мс. Панель пересобирается на каждое изменение, поэтому сдвиг проигрывается явно (Web Animations) — переход с нуля на только что вставленном элементе браузер не запускает. При открытии другого дела подсветка ставится сразу, без переезда. Каждая строка растягивается на всю ширину: время, сегменты, категория и действия делят её без пустот. Кнопка «без привязки ко времени» и всё, что она открывает (дробление, «от», «до», «открепить»), — нежно-голубые; незаданная граница окна ещё бледнее.

Настройки, которые есть только у дел без привязки ко времени, живут в **отдельной строке**, — у событий «ко времени» её нет вовсе. Строка выдвигается **только в момент смены типа**: при любом другом изменении (характер, дробление, категория) панель пересобирается, но строка остаётся на месте и заново не всплывает.

**Открытие.** Шторка раскрывается сверху вниз, плавно сдвигая календарь (0,24 с). Анимация играет только при открытии — переключатели внутри её не перезапускают. После раскрытия календарь подкручивается так, чтобы выбранное дело оказалось **по центру оставшейся видимой части** (ниже липких шапок дней) — не приходится искать его под панелью.

### D.23 Перенос фразой (✨)
В шторке события кнопка ✨ открывает поле «Куда перенести?». Понимаются три формы:
- **день и время** («завтра в 15:00») — событие встаёт ровно туда;
- **только день** («перенеси на сегодня», «на завтра», «в понедельник») — приложение само выбирает **ближайшее свободное окно** нужной длины в этом дне: не в прошлое, в рабочих часах, с обязательными буферами и без наложений. Если окна нужной длины в дне нет — так и сказано, событие остаётся на месте;
- **день и длительность** («завтра на час») — длительность меняется, только если названа явно.

### D.9 Разрешение конфликтов между делами
- **Случай B (авто, по умолчанию):** новое событие «ко времени» накладывается на подвижное → подвижное **молча** перетекает вокруг события (обычный переплан), в том числе если для этого его надо открепить или раздробить. Может сдвинуться несколько задач — с сохранением привязок ко времени и дедлайнов. Проверка делается пробным перепланом на копии плана: спрашиваем только тогда, когда после переноса задача осталась **без места до своего дедлайна** (`atRisk`). Само по себе наложение поводом для вопроса не является.
- **Случай A (предложение):** новое событие накладывается на другое **неподвижное** (оба «ко времени» / locked) → молча не накладываем. «Проигравшим» считаем более позднее по `created_at`; помечаем `conflict = { withTitle, suggestions }` и предлагаем **3 ближайших свободных окна** (дедлайн не ограничивает — это «куда вообще можно»). Возможные места подсвечиваются призрачными блоками в календаре, ниже — теми же 3 вариантами кнопками; выбор варианта переносит событие и снимает конфликт. Рядом — кнопка **«Перенести другое событие»**: включает режим выбора, в котором клик по мешающему делу сдвигает **его** на день вперёд.

## E. Изменения модели данных (относительно §4)

- **Новое поле `nature`:** `strategic | tactical` (см. ось B).
- **`recurrence`:** правило повторения (`каждые N дней` / `по будням` / …) — нужно уже в v1 из-за примера с тренировкой (сдвигает базовую повторяемость из P1).
- **Статус разведён на две оси:** `status` (жизненный цикл: `unscheduled → scheduled → in_progress → done`) **и** отдельный флаг `at_risk` + поля `at_risk_reason` / `shortfall_minutes`. Задача может быть частично размещена **и** at_risk одновременно.
- **Чанк — самостоятельная сущность:** `{ id, date, start_time, duration, locked, status }`. Нужно для поштучного лока (R8), отметки «сделано» и рефлоу. `status = done` у куска — выполнение по частям (D.27): такой кусок не двигается, не срастается и считается уже размещённым временем.
- **`confidence` на извлечённых полях:** для подсветки красным на экране подтверждения.
- **`timezone`:** дедлайны и граница «сейчас» считаются относительно зоны; для офлайн-PWA в поездках хранить в UTC, показывать в локальной.
- **`category`** — ссылка на настраиваемый пользователем список, а не фиксированный enum.
